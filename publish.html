Publish

Versions that
stay.

Publishing is for good. Pick a build and b0-x writes it to Bitcoin SV as a website ordinal, served through ORDFS and the b0-x gateway.

In development

How a version is stored

A directory of inscriptions.

Each file in your build is inscribed as its own ordinal with its content type. Then one more inscription, the manifest, lists them: an ord-fs/json directory that maps paths to inscriptions.

An ORDFS gateway reads the manifest and serves your site, so /index.html, /app.css and /img/logo.png resolve the way they did on your host.

// manifest (ord-fs/json), illustrative
{
  "index.html":   "ord://8f2c…e11a_0",
  "app.css":      "ord://41b9…07cd_0",
  "app.js":       "ord://c3d0…9a12_0",
  "img/logo.png": "ord://77ae…f0b3_0"
}

Versions

New version, new manifest.

Numbered

Each publish creates v1, v2, v3… Every version is its own manifest, so old versions keep working at their own address.

Only what changed

The plan: unchanged files point at the inscriptions they already have, so an update only pays for changed files plus a new manifest.

Named

Your OpNS name points at whichever version you say is current.

Permanence

What "for good" means.

Once a version is inscribed it is part of the Bitcoin SV ledger. We can't edit it or take it down, and neither can anyone else. That's the point, and it's also the warning: don't publish secrets, private data, or anything you don't have the rights to. b0-x will scan builds for obvious keys and .env files before it asks you to confirm.

A copy on a normal web host can be deleted at any time. On-chain versions can't.
